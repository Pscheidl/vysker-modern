# PostgreSQL schema and naming

The application uses PostgreSQL 18 through SQLx 0.9. SQLite is no longer supported.
This website has not been deployed, so its former SQLite migrations have been
replaced by a single PostgreSQL baseline, `migrations/0001_initial.sql`. No import
or upgrade of old development SQLite databases is performed. Existing local
SQLite files can remain as historical development data.

Tables, columns, indexes, triggers and state values use English. Table names are
plural and columns use `snake_case`. The established `audit_log` name and SQLx's
internal `_sqlx_migrations` table are exceptions. Municipal content stays Czech.

## Tables

| Table | Purpose |
| --- | --- |
| `categories` | Notice board categories |
| `notices` | Drafts, published notices and permanent archive records |
| `documents` | General documents |
| `attachments` | Metadata, SHA-256 and binary contents |
| `pages` | Content pages |
| `administrators` | Accounts with salted Argon2id password hashes |
| `sessions` | Hashed session and CSRF tokens |
| `rate_limits` | Atomic request counters |
| `subscribers` | Newsletter subscribers |
| `subscription_tokens` | Hashed verification and unsubscribe tokens |
| `mail_queue` | Durable queue and SMTP acceptance history |
| `audit_log` | Operation history protected during retention |
| `consent_notices` | Immutable subscription wording and policy snapshots |
| `subscription_consents` | Opt-in, confirmation and withdrawal evidence |
| `privacy_maintenance` | Transactional retention cleanup guards |
| `notice_events` | Publication evidence and incident history |

Identifiers use `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Publication and
withdrawal days use `DATE`, flags use `BOOLEAN`, attachments use `BYTEA`.
Application and evidence timestamps retain their UTC RFC3339 text representation,
while session, token and queue deadlines use `BIGINT` Unix seconds. JSON snapshots
remain text with PostgreSQL JSON validation, preserving the serialized evidence
and API format. Queries use numbered bind parameters, `RETURNING` and PostgreSQL
JSON operators.

`retain_attachments` defaults to `false` and controls only attachment contents.
A minimal notice record always remains. PostgreSQL triggers prevent deletion or
truncation of notice records and attachment metadata. Audit and publication
evidence updates are rejected. Deletion is allowed only through the retention
guards used by the application's maintenance transaction. The database owner can
alter schema objects, so operator access must remain restricted.

## Transactions and concurrency

Multi-step business writes acquire a transaction-scoped PostgreSQL advisory lock
for the application schema. It serializes publication, account changes, subscription
transitions and retention without blocking ordinary readers. Password hashing
and SMTP calls run outside that transaction. The lock is released on commit,
rollback or connection loss. This deliberately favors simple correctness for
municipal editorial traffic over maximum concurrent write throughput.

Mail workers claim queue entries atomically with `FOR UPDATE SKIP LOCKED` and a
lease token. Search counts and result pages share a repeatable-read snapshot.
Rate limits use atomic upserts. Unique constraints protect normalized email
addresses, active consents and notification deduplication keys.

## Development and test instances

`nix develop` provides PostgreSQL 18, its client tools and Python psycopg, then
starts a local database on `127.0.0.1:5432`. Its data lives in ignored
`data/postgres/`. Use `scripts/postgres.sh status` or `scripts/postgres.sh stop`
to manage it. Set `OBEC_PG_PORT` before entering Nix to choose another port.
The local account and database are `vysker`, with development password `vysker`.

`docker compose up -d postgres mailpit` provides PostgreSQL and test SMTP instead.
PostgreSQL data lives in the named `postgres-data` volume. Do not start both local
instances on the same port. `docker compose down` preserves the volume.

`./scripts/test.sh` creates its own temporary PostgreSQL cluster by default.
If `TEST_DATABASE_URL` is supplied, it uses that server to create and later drop a
randomly named test database. Rust tests each receive a separate schema. The
account needs `CREATEDB` on the test server, but production accounts do not.
See [testing.md](testing.md) for SMTP, browser and recovery checks.

## Production connections and recovery

Set `OBEC_DATABAZE` to a PostgreSQL URL or `OBEC_DATABAZE_FILE` to a secret file
containing one. These settings are mutually exclusive. For a remote managed
server, configure TLS with `sslmode=verify-full` and the provider's trusted CA
where required. Connection passwords must be URL-encoded and never committed.

Production Compose creates a separate non-superuser application role and keeps
the PostgreSQL port private. Its volume persists independently of application
containers. Managed PostgreSQL can replace this service by supplying its connection
URL and operator backup policy.

Backups use PostgreSQL `pg_dump` custom archives. Recovery uses `pg_restore` into
a new database and invalidates subscriptions and sessions before the operator
switches the application. Client tools must match the server major version or be
compatible with it. See [operations.md](operations.md).

After first deployment, preserve applied SQLx migrations and add subsequent
schema changes as new migrations. A Git history squash alone must not rewrite
migration checksums in an already deployed database.
